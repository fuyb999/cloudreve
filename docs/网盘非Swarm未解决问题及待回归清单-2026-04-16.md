# 网盘非Swarm未解决问题及待回归清单

更新时间：2026-04-16 23:30 CST

## 1. 文档定位

本文档只记录两类内容：

1. Cloudreve 非 Swarm 场景下，当前仍未彻底收口的问题。
2. 已经补过代码，但必须继续做真实环境回归验证的链路。

本文档不重复记录已经稳定且低风险的能力。

## 2. 未解决问题

### BUG-001 OIDC scope 契约仍未与 Authverse 完全统一

级别：高

现状：

1. Cloudreve 默认 `oidc_scope` 仍包含：
   `openid profile email user_info user.read UserInfo.Read Admin.Read Files.Read Files.Write`
2. 对应代码：
   - `pkg/setting/provider.go`
   - `service/user/oidc.go`
3. 但统一认证侧当前并没有完全按同一套 scope 契约对外稳定声明。
4. Cloudreve 公共授权代理链路又确实会依赖 `Admin.Read / Files.Read` 这类 scope。

影响：

1. 真实联调时容易出现“登录成功，但某条公共资源或授权链路仍提示缺 scope”。
2. 文档、默认配置、统一认证 discovery、实际接口能力仍可能不一致。

建议动作：

1. 把 Cloudreve 所需 scope 清单与 Authverse discovery、SQL 默认值、前端表单一次性对齐。
2. 如果后续要收缩到标准 scope，就要同步改掉 Cloudreve 运行时对自定义 scope 的依赖。

### BUG-002 OIDC live introspection 语义与历史文档不一致，且会放大认证中心依赖

级别：中

现状：

1. 当前 `TryVerifyOIDCAccessToken()` 命中本地缓存后，仍会再次调用 introspection。
2. 对应代码：
   - `service/user/oidc_token.go`
3. 这样做有利于统一登出和撤销立即生效，但也意味着认证中心更接近运行时硬依赖。

影响：

1. 历史文档中的“后续优先走本地缓存，不再每次远程访问”不再成立。
2. 如果统一认证中心短时不可用，Cloudreve OIDC 请求链路仍可能受影响。

建议动作：

1. 先把运行手册更新到当前事实。
2. 再决定是否需要引入更强的本地缓存窗口或降级策略。

### BUG-003 OIDC remote binding 配置来源不够透明

级别：中

现状：

1. 当前默认会尝试通过 `well-known` 推导并请求：
   `/app-api/authz/integration/runtime/binding-config`
2. 对应代码：
   - `service/user/oidc_runtime.go`
3. 远端拉取失败后会 fallback 到本地设置，但页面和用户视角不容易分辨当前实际生效来源。

影响：

1. 排查时容易出现“页面配置正确，但实际跑的是 fallback 本地值”的误判。
2. 绑定编码、discovery 地址、runtime 配置三者不一致时，定位成本高。

建议动作：

1. 在管理页或日志中明确输出当前配置来源是 `remote` 还是 `local fallback`。
2. 把 `bindingCode`、推导 URL、fallback 条件写入正式运行手册。

### BUG-004 统一认证 授权联动链路较长，运行时诊断仍不够直观

级别：中

现状：

1. Cloudreve 当前已经同时依赖：
   - OIDC remote binding
   - 公共文件远程可见性检查
   - 管理端公共资源快照与规则入口
2. 对应代码：
   - `service/user/oidc_runtime.go`
   - `service/publicshare/service.go`
   - `routers/router.go`
3. 但从页面或日志上看，用户不容易一眼分清：
   - 当前用的是哪套绑定编码
   - 当前资源快照来自本地还是远程公共授权视图
   - 当前动作被拒绝，是本地 capability 还是统一授权远程边界导致

影响：

1. OIDC、网盘授权、公共文件动作拒绝三类问题容易混在一起。
2. 排查“为什么这个按钮有/没有、为什么接口过/不过”时成本高。

建议动作：

1. 在管理端增加更显式的运行时诊断信息。
2. 至少把 `bindingCode`、远程可见根、动作决策来源暴露给调试视图。

### BUG-006 节点能力与内容处理能力并存，用户理解成本仍偏高

### REG-010 `fts_sync_folders=0` 时删除文件夹后 ES 残留待回归

当前状态：用户发现疑似问题，待真实环境复现与回归

现象：

1. “同步文件夹”开关关闭时，删除文件夹后疑似没有同步到 ES。
2. 对应设置项为 `fts_sync_folders=0`。
3. 用户后续补充记忆中操作是“直接彻底删除”，因此优先排查直接删除目录后的 `IndexToDelete`、delete-only `full_text_index` 任务入队和任务执行状态。

当前代码判断：

1. `fts_sync_folders=0` 只应控制“文件夹自身是否写入 ES”。
2. 删除文件夹时，目录下文件仍应递归触发 ES 清理。
3. 已有代码级保护显示：
   - 默认删除会递归收集子文件 ID 并排 `full_text_delete`。
   - 直接删除会通过 `IndexToDelete` 递归传递子文件 ID。
   - delete-only reconcile 遇到文件消失或进入回收站时应删除 ES 文档。
4. 2026-06-16 代码排查新增高风险根因假设：普通删除到回收站前的 `collectFTSRecursiveFileIDs()` 通过 `DBFS.Walk()` 收集子树 ID，`DBFS.Walk()` 受用户组 `max_walked_files` 限制；当目录子树超过上限时会返回 `ErrFileCountLimitedReached`，但当前收集函数忽略 walk 错误，可能导致目录删除成功而只为部分子文件排 ES 删除任务。
5. 直接删除和回收站定时硬删除走 `DBFS.Delete()`，内部使用近似无限遍历上限并会返回 walk 错误，因此当前风险优先聚焦“普通删除目录到回收站”。
6. 对于用户补充的“直接彻底删除”，更高优先级的风险点是：删除时 `FTSEnabled(ctx)` 为 false 导致 `IndexToDelete` 不排任务、`queueFullTextReconcile()` 入队失败只打 warning、`full_text_index` delete-only 任务处于 error/suspending、或 `DBFS.Delete()` 返回 aggregate error 使 `manager.Delete()` 在 `processIndexDiff()` 前返回。

待回归重点：

1. `fts_enabled=1`、`fts_sync_folders=0` 下，个人目录默认删除到回收站后，目录下所有可索引子文件 ES 0 命中。
2. 同条件下，公共目录默认删除到回收站后，公共/owner 投影字段均无残留。
3. 个人目录和公共目录直接删除（`skip_soft_delete=true`）后，子文件 ES 全部清理。
4. 直接彻底删除目录后，所有被删除子文件都必须出现在 delete-only `full_text_index` 任务或等价删除任务中，任务最终完成且 ES 0 命中。
5. Tika/ES 任务 processing 或 pending 时删除父目录，迟到 `full_text_index` 不得把已删除子文件写回 ES。
6. 低 `max_walked_files` 或大目录场景下，普通删除目录后不得出现只清理部分子文件 ES 的情况。
7. 同时核验 Cloudreve Search 与统一检索结果，不得只看 ES `_count`。

必须保留证据：

1. 残留或清理后的 ES 文档 JSON，至少含 `_id/file_id/entity_id/owner_uri/public_uri/tree_path/search_paths/search_uris/latest_version/synchronized_at`。
2. PG `files`、`metadata`、`tasks` 相关行。
3. Cloudreve 日志中的 correlation id、`full_text_delete/full_text_index`、`Full text indexing paused`、`failed to delete index` 等关键字。
4. 当时 `fts_enabled`、`fts_sync_folders`、`fts_index_type`、ES index 名称、用户组 `max_walked_files` 和队列指标。
5. 若复现大目录截断，需记录删除前完整子文件 file_id 清单、任务 private_state 中实际排队 file_id、ES 残留 file_id 差集。
6. 若复现直接彻底删除，需记录 `skip_soft_delete=true` 请求体、接口响应、相关 `full_text_index` delete-only 任务 private_state、任务状态、队列 warning/error 日志和 ES 残留 file_id 差集。

通过标准：

1. 文件夹自身不索引可以接受。
2. 删除文件夹后，其所有可索引子文件必须从 ES、Cloudreve Search、统一检索中消失。
3. 任务状态必须 completed，或 error/suspending 有明确原因与处理结论。

详细用例：

- `docs/三系统OAuth-网盘检索授权真实环境联调测试计划-2026-05-21.md` 的 `18.5.12`

4. 抽取失败时 `latest_version` 与附件树落 ES。
5. 节点能力并存下的调度回归。

## 5. 当前结论

截至 2026-04-16，Cloudreve 非 Swarm 场景下真正需要优先收口的是三件事：

1. OIDC scope 与运行时配置来源透明化。
2. 公共文件 `owner_id / visibility / button / metadata patch / ES` 整链路真实回归。
3. 删除文件夹、回收站、直接删除、定时回收与 ES 清理的一致性回归。
