# 网盘非Swarm未解决问题及待回归清单

更新时间：2026-04-16 23:30 CST

## 1. 文档定位

本文档只记录两类内容：

1. Cloudreve 非 Swarm 场景下，当前仍未彻底收口的问题。
2. 已经补过代码，但必须继续做真实环境回归验证的链路。

本文档不重复记录已经稳定且低风险的能力。

## 2. 未解决问题

### BUG-001 OIDC scope 契约仍未与 Authverse 完全统一

级别：高

现状：

1. Cloudreve 默认 `oidc_scope` 仍包含：
   `openid profile email user_info user.read UserInfo.Read Admin.Read Files.Read Files.Write`
2. 对应代码：
   - `pkg/setting/provider.go`
   - `service/user/oidc.go`
3. 但统一认证侧当前并没有完全按同一套 scope 契约对外稳定声明。
4. Cloudreve 公共授权代理链路又确实会依赖 `Admin.Read / Files.Read` 这类 scope。

影响：

1. 真实联调时容易出现“登录成功，但某条公共资源或授权链路仍提示缺 scope”。
2. 文档、默认配置、统一认证 discovery、实际接口能力仍可能不一致。

建议动作：

1. 把 Cloudreve 所需 scope 清单与 Authverse discovery、SQL 默认值、前端表单一次性对齐。
2. 如果后续要收缩到标准 scope，就要同步改掉 Cloudreve 运行时对自定义 scope 的依赖。

### BUG-002 OIDC live introspection 语义与历史文档不一致，且会放大认证中心依赖

级别：中

现状：

1. 当前 `TryVerifyOIDCAccessToken()` 命中本地缓存后，仍会再次调用 introspection。
2. 对应代码：
   - `service/user/oidc_token.go`
3. 这样做有利于统一登出和撤销立即生效，但也意味着认证中心更接近运行时硬依赖。

影响：

1. 历史文档中的“后续优先走本地缓存，不再每次远程访问”不再成立。
2. 如果统一认证中心短时不可用，Cloudreve OIDC 请求链路仍可能受影响。

建议动作：

1. 先把运行手册更新到当前事实。
2. 再决定是否需要引入更强的本地缓存窗口或降级策略。

### BUG-003 OIDC remote binding 配置来源不够透明

级别：中

现状：

1. 当前默认会尝试通过 `well-known` 推导并请求：
   `/app-api/authz/integration/runtime/binding-config`
2. 对应代码：
   - `service/user/oidc_runtime.go`
3. 远端拉取失败后会 fallback 到本地设置，但页面和用户视角不容易分辨当前实际生效来源。

影响：

1. 排查时容易出现“页面配置正确，但实际跑的是 fallback 本地值”的误判。
2. 绑定编码、discovery 地址、runtime 配置三者不一致时，定位成本高。

建议动作：

1. 在管理页或日志中明确输出当前配置来源是 `remote` 还是 `local fallback`。
2. 把 `bindingCode`、推导 URL、fallback 条件写入正式运行手册。

### BUG-004 统一认证 授权联动链路较长，运行时诊断仍不够直观

级别：中

现状：

1. Cloudreve 当前已经同时依赖：
   - OIDC remote binding
   - 公共文件远程可见性检查
   - 管理端公共资源快照与规则入口
2. 对应代码：
   - `service/user/oidc_runtime.go`
   - `service/publicshare/service.go`
   - `routers/router.go`
3. 但从页面或日志上看，用户不容易一眼分清：
   - 当前用的是哪套绑定编码
   - 当前资源快照来自本地还是远程公共授权视图
   - 当前动作被拒绝，是本地 capability 还是统一授权远程边界导致

影响：

1. OIDC、网盘授权、公共文件动作拒绝三类问题容易混在一起。
2. 排查“为什么这个按钮有/没有、为什么接口过/不过”时成本高。

建议动作：

1. 在管理端增加更显式的运行时诊断信息。
2. 至少把 `bindingCode`、远程可见根、动作决策来源暴露给调试视图。

### BUG-005 公共文件按钮配置体验仍偏重模板和逐动作配置

级别：中

现状：

1. 当前 capability 是按动作逐项映射的。
2. 对应代码：
   - `pkg/filemanager/fs/dbfs/public_navigator.go`
3. 不套模板时，用户确实需要逐项配置 `upload/create/rename/delete/share/...`。

影响：

1. 容易被误认为“按钮权限有 bug”。
2. 实际上更多是当前授权模型与页面交互的可理解性不足。

建议动作：

1. 在前端页面上把“可见性”和“动作集”分层展示得更清楚。
2. 提供更强的模板预设与批量选择交互，减少逐项配置成本。

### BUG-006 节点能力与内容处理能力并存，用户理解成本仍偏高

级别：中

现状：

1. 当前节点能力同时存在：
   - `create_archive`
   - `extract_archive`
   - `remote_download`
   - `content_processing`
2. 后台虽然已有节点页、队列页、任务页、首页巡检入口，但对非研发用户来说仍然不够直观。
3. 容易出现一种误解：
   “既然有内容处理节点，为什么压缩/解压还不是走同一能力”

影响：

1. 节点相关问题容易被误判成调度 bug。
2. 内容处理节点与传统 archive/extract 节点的职责边界不够一眼可见。

建议动作：

1. 在节点管理页补更明确的能力说明和任务覆盖范围。
2. 在 runbook 中单独说明哪些任务属于 `content_processing`，哪些仍是独立 capability。

### BUG-007 ES 字段事实已经可用，但稳定展示契约仍未完全标准化

级别：中

现状：

1. 目前 ES 中已经有 `owner_id/tree_path/content/attachments/latest_version` 等事实字段。
2. 对应代码：
   - `pkg/searcher/indexer.go`
   - `pkg/searcher/indexer/elasticsearch.go`
3. 但“哪些字段是稳定给上层展示和统一检索消费的契约”仍未正式收口。

影响：

1. 运行时能查，不代表上层展示与跨系统消费已经完全稳定。
2. 后续若继续加展示字段，仍可能出现文档大于代码现状的问题。

建议动作：

1. 单独沉淀一版 Cloudreve ES 字段契约文档，只保留当前真实输出。
2. 区分“事实字段”和“上层展示字段”。

### BUG-008 第三方抽取可用前提仍容易被误配

级别：中

现状：

1. 第三方抽取只适用于可被第三方直接访问的对象存储策略。
2. `local`、应用层加密文件默认不发第三方。
3. 对应文档与代码：
   - `docs/fts-third-party-extractor-runbook-不需要维护.md`
   - `pkg/filemanager/manager/fulltextexternal_task.go`
   - `pkg/filemanager/manager/fulltext_slave.go`

影响：

1. 若联调账号仍使用 `local` 策略，会误以为第三方抽取失效。
2. 若未理解加密边界，也会误以为 Kafka 或任务状态机有 bug。

建议动作：

1. 在后台配置页增加更明确的 eligibility 提示。
2. 在任务诊断里直接说明本次未发送第三方的原因。

## 4. 推荐回归顺序

### 4.1 P0

1. OIDC scope 契约统一。
2. Cloudreve 单机真实环境下的登录、远程 binding、公共授权联动、上传、公共文件上传、在线解压、全文抽取、ES 同步。
3. 抽取失败时 `latest_version` 与附件树落 ES。
4. 节点能力并存下的调度回归。

### 4.2 P1

1. 公共文件按钮与动作矩阵回归。
2. 第三方抽取 success / fallback 双场景回归。
3. 内容处理从节点真实回归。
4. 管理端公共资源快照与远程动作试算回归。

## 5. 当前结论

截至 2026-04-16，Cloudreve 非 Swarm 场景下真正需要优先收口的是三件事：

1. OIDC scope 与运行时配置来源透明化。
2. 公共文件 `owner_id / visibility / button / metadata patch / ES` 整链路真实回归。
3. 全文抽取失败与第三方回退场景下，`latest_version`、附件树、sidecar、ES 的一致性回归。
