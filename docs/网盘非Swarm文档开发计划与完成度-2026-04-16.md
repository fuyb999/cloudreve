## 3. 总体判断

### 3.1 大方向没有跑偏

当前网盘侧主线与此前设计总体一致：

1. `Authverse` 仍是 OIDC Provider，`Cloudreve` 仍是 OIDC Client + 资源服务端。
2. 公共文件授权仍是“先可见，再操作”的运行时模型，按钮显隐只是 capability 映射结果，不是另一套权限体系。
3. 内容处理已经统一收口到 `NodeCapabilityContentProcessing`，不再是全文、媒体、文档检查各自单独扩展。
4. 全文抽取仍以 `sidecar -> 标准化文档 -> ES Upsert` 为主链，没有把第三方抽取直接接成新的 ES 写入方。
5. 公共文件与检索/全文链路的边界已经逐步从 `owner_id` 误用，收敛回 `tree_path + public visibility + owner` 的组合模型。

### 3.2 主要偏差不是架构，而是“旧文档已过时”

本轮发现的偏差主要是历史文档结论滞后于代码，而不是主方向错误：

1. `统一认证-网盘OIDC接入说明-不需要维护.md` 里“命中缓存后不再每次远程访问认证中心”的描述，已不符合当前代码。
2. `content-processing-node-plan.md` 中关于“尚未实现 `NodeCapabilityContentProcessing`”的评估背景已经过时。
3. `fts-third-party-extractor-plan.md` 里的方案设计大部分已经在代码中落地，真正的运行事实应以 `fts-third-party-extractor-runbook.md` 为准。
4. `browser-integration-test-plan-v2.md` 已被 `browser-integration-test-plan.md` 替代，不应继续作为执行主文档。

## 5. 已落地的关键能力

### 5.1 OIDC 接入主链已完成

当前代码已实现：

1. 登录准备与授权码换票：
   - `service/user/oidc.go`
2. Access token 校验、刷新、登出、撤销回调、Back-Channel Logout：
   - `service/user/oidc_token.go`
3. 运行时按绑定编码从统一授权侧拉取配置：
   - `service/user/oidc_runtime.go`
4. 默认 OIDC 配置项与表单字段：
   - `pkg/setting/provider.go`
   - `pkg/setting/types.go`

当前还应明确一个事实：

`TryVerifyOIDCAccessToken()` 即使命中本地缓存，也会再做一次 live introspection，以便统一登出和撤销立即生效。因此当前实现更偏向一致性优先，而不是纯本地缓存优先。

### 5.2 统一认证 远程集成主链已成型

当前 Cloudreve 与统一认证/授权中心的集成，已经不只是一套本地 OIDC 表单，而是包含两条远程联动主线：

1. OIDC remote binding：
   - 默认 `oidc_config_mode=remote`
   - 默认 `oidc_binding_code=cloudreve-main`
   - 通过 `well-known` 推导并请求 `/app-api/authz/integration/runtime/binding-config`
   - 对应代码：
     - `pkg/setting/provider.go`
     - `pkg/setting/types.go`
     - `service/user/oidc_runtime.go`
2. 公共文件授权远程检查与管理入口：
   - 运行时远程可见性与动作检查：
     - `/api/v4/public/remote/visibility`
     - `/api/v4/public/remote/check`
   - 管理端公共根、资源快照、子资源浏览、规则写回、mock profile：
     - `service/publicshare/service.go`
     - `routers/router.go`

这说明当前 Cloudreve 与 统一认证 的集成已经包含：

1. 登录配置远程下发
2. 公共文件资源快照回填
3. 公共文件动作试算与可见性调试
4. 管理端公共资源建模入口

因此 `统一认证-网盘OIDC接入说明-不需要维护.md` 与 `统一认证-网盘授权联调说明-不需要维护.md` 仍然都有保留价值，前者偏 OIDC 接入手册，后者偏授权中心联调与公共文件边界回归。

### 5.3 公共文件 owner 模型已收敛

当前代码已经明确：

1. 公共根目录由系统虚拟 owner 持有：
   - `inventory/public_root.go`
2. 公共文件根目录下的新建目录、上传文件，其 owner 优先写当前登录用户：
   - `pkg/filemanager/fs/dbfs/dbfs.go`
   - `pkg/filemanager/fs/dbfs/upload.go`

这意味着当前语义是：

1. 只有公共根保留系统 owner 语义。
2. 根下子资源回归真实创建人。
3. 后续全文索引、检索授权、操作权限计算不应再把“公共资源都归 `-1`”当成前提。

### 5.4 公共文件可见性与按钮动作已收口

当前 `public_navigator` 已将动作映射为 capability：

- `download`
- `direct_link`
- `archive`
- `upload`
- `create`
- `rename`
- `copy`
- `move`
- `delete`
- `share`
- `metadata`

对应代码：

- `pkg/filemanager/fs/dbfs/public_navigator.go`

当前模型不是“开一个总开关就拥有全部按钮”，而是：

1. 可见性是前置条件。
2. 具体按钮逐动作映射。
3. 模板只是批量配置动作，不是另一套运行时语义。

### 5.5 节点能力与主从编排主线没有被内容处理抽象取代

当前节点侧不是“所有任务都统一并到 content processing”，而是两层结构并存：

1. 传统独立 capability 仍保留：
   - `create_archive`
   - `extract_archive`
   - `remote_download`
2. 新增统一内容处理 capability：
   - `content_processing`

对应代码：

- `inventory/types/types.go`
- `inventory/migration.go`
- `pkg/cluster/pool.go`
- `pkg/filemanager/workflows/archive.go`
- `pkg/filemanager/workflows/extract.go`

当前主从编排语义是：

1. 压缩、解压、远程下载仍按原有 capability 分配节点。
2. 全文抽取、媒体元数据、文档识别、部分缩略图链路，统一走 `NodeCapabilityContentProcessing`。
3. slave 侧统一通过 `/api/v4/slave/task` 下发和查询任务：
   - `service/node/task.go`

因此 `content-processing-node-plan.md` 里的“统一抽象”是增量收口，不是替换现有所有节点能力。

### 5.6 内容处理从节点统一抽象已落地

这说明 `content-processing-node-plan.md` 里大量“尚未具备”的背景段落已经变成历史背景，不再代表当前完成度。

1. OIDC token 本地缓存并不意味着后续完全不访问认证中心。
2. 当前更准确的表述应是：
   “首次校验后会建立本地映射缓存，但为了统一登出和撤销立即生效，后续请求仍可能做实时 introspection。”

其中以下内容已明显过时：

1. “没有 `NodeCapabilityContentProcessing`”

3. “没有统一内容处理队列”

这些点当前都已在代码中落地，因此该文档仍可作为设计背景与术语说明保留，但不能再作为“当前缺失能力清单”。

同时该文档后半段关于：

1. 内容处理队列
2. 节点页过滤
3. 任务页聚合
4. 首页和队列页的巡检入口

这些内容已基本进入“实现现状总结”范畴，应按当前实现理解，而不再只是规划。

### 6.3 `browser-integration-test-plan-v2.md` 已失去主文档价值

当前仓库内：

### 6.4 `fts-third-party-extractor-plan.md` 已被代码和 runbook 吸收

这份文档当前仍保留价值，原因不是历史回忆，而是其中已经吸收了多轮关键代码回归结论，尤其包括：
