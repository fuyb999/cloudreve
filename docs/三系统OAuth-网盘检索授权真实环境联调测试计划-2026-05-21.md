# 三系统 OAuth、网盘、检索、授权真实环境联调测试计划

> **For agentic workers:** REQUIRED SUB-SKILL: Use `superpowers:verification-before-completion` before marking any Gate as complete. This document is an execution plan; every step uses checkbox syntax for tracking and must be filled with browser evidence, logs, failure reason, modification path, and regression result.

**Goal:** 在真实 Chrome、真实服务、真实 PG/Redis/ES/Tika 环境下，按顺序验证统一认证、网盘、统一检索、网盘授权、任务队列、ES 同步和认证后台页面是否可稳定联调。

**Architecture:** 先以单节点 Cloudreve 建立行为基线，再切换主从协调模式回放同一批任务；统一认证负责 Cloudreve/Search 登录和公共文件授权，Cloudreve 负责文件操作和任务队列，Search 在自身策略基础上叠加 Cloudreve 可见性边界。

**Tech Stack:** Chrome、Cloudreve Go 后端与 `assets` 前端、Authverse React 前端、`authverse-backend` Java 17 后端、Search 前端、PostgreSQL、Redis、Elasticsearch、Tika、可选离线下载器、Syncthing 客户端 OAuth 拉起验证。

## 0. 本轮范围

### 0.1 本轮必须测试

1. 网盘、检索、统一认证三系统 OAuth/OIDC 登录联调；联调成功后，在同一 Chrome Profile 中拉起同步客户端并通过网盘内置 OAuth 完成认证。
2. 网盘个人文件所有操作，按前端能力入口补全文件/文件夹动作。
3. 网盘公共文件所有操作，联合统一认证中的网盘授权策略模板测试可见性和可操作性，覆盖用户、角色、部门、上下级部门、排除角色等场景，禁止越权访问。
4. 统一检索授权，Cloudreve 索引必须在公共文件可见性基础上叠加检索自身策略；新增自定义检索策略模板并结合主体测试。
5. 网盘单节点与主从节点任务协调：解压、压缩、文件抽取、ES 同步、离线下载、队列任务监控；结合 ES、Tika、PG 做联合调试。
6. 网盘中文件变动同步到 ES 的正确性，结合所有文件操作，并在 50000 文件基数上做压力测试。
7. 统一认证所有页面和功能模块测试。
8. 全部阶段完成后，从头按相同流程做一次全流程回归。

### 0.2 本轮明确不测试

原需求中的第 2、3 项本轮先不执行：

1. 不测试 Syncthing 上传、新建、移动、复制、重命名、删除同步效果。
2. 不测试 Syncthing 50000 文件同步压力。
3. 不测试 Syncthing 设备注册、解绑、配置恢复等设备生命周期流程。

保留的同步客户端相关测试只有一项：三系统 OAuth 联调成功后，在同一浏览器会话中拉起同步客户端，通过 Cloudreve 内置 OAuth 完成客户端认证。

#### 8.4.1 owner 可见性边界

`owner` 适合作为“维护动作”的兜底条件，例如 owner 可重命名或维护自己创建的公共文件；但不要在部门/角色工作区的基础可见性里随手加 owner 限制，除非产品语义就是“只给 owner 看”。

原因：

1. 公共一级目录的 owner 通常是创建它的超级管理员或系统账号；如果 visibility 只按 owner 或强依赖 owner，部门管理员和普通部门成员会被错误排除。
2. 公共子资源 owner 是实际创建人或派生链路的归属人，复制、移动、恢复等操作后 owner 可能和“应该可见的部门/角色范围”不一致。本轮 `file_id=299` 就是复制件保留实体 `145`，但归属到目标公共目录 owner `180`。
3. 统一检索的边界已经是 `searchPolicyAllow AND (owner_id = currentUser OR publicVisibilityBoundary)`。个人文件 owner 边界和公共文件 visibility 边界应分层表达；把 owner 混入公共 visibility 容易把公共共享目录收窄成个人可见，造成漏授权，也会让排查 Search 越权/漏权更困难。

推荐规则：公共目录 visibility 用部门、角色、指定用户、上下级部门等共享主体表达；owner 只用于 `public-owner-maintain` 这类明确的 owner 维护模板，或作为 action 规则的补充条件。

#### 8.4.2 为什么必须做收尾核验

浏览器接口步骤通过只能证明同步请求没有被拒绝，不能证明异步 `document_inspect/full_text_index/full_text_copy` 已经把最终状态写入 metadata 和 ES。本轮发现的问题正是“文件操作已成功，但复制后的 FTS 任务用旧 URI patch metadata，可能留下旧 ES 文档或旧文件名”。因此公共权限回归必须在操作后追加三类收尾：

1. 查 `tasks`：所有本轮任务必须进入 `completed`，受控失败必须有 `public_state.error/error_history`。
2. 查 DB：`files` 当前名称、`tree_path`、`owner_id`、`primary_entity` 和 `metadata sys:fulltext_index` 必须一致。
3. 查 ES：已删除文件不能命中；移动、复制、重命名后的 `file_name/public_uri/owner_uri/search_paths/search_uris/path_text/content/latest_version` 必须和 PG 当前文件一致。
