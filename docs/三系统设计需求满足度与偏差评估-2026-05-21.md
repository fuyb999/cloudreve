## 4. 旧设计需求基线

旧设计的核心诉求可以归纳为八类：

| 编号 | 需求基线 | 关键验收口径 |
| --- | --- | --- |
| R1 | 三系统统一 OIDC / OAuth 登录 | 登录任一端后，Cloudreve、Search、Authverse 的 token 与会话链路一致；撤销、刷新、登出能闭环 |
| R2 | 统一接入注册中心与运行时绑定 | OIDC client、scope、discovery、SSO、回调地址由统一认证集中管理，Cloudreve/Search 不各自漂移 |
| R3 | Cloudreve 公共文件授权 | 公共文件先判断可见性，再判断动作；用户、角色、部门等主体策略不允许越权 |
| R4 | 统一检索授权 | Search 查询必须在用户主体策略基础上执行；Cloudreve 来源必须叠加网盘可见边界，不能通过检索扩大权限 |
| R5 | 统一授权 DSL | 同一管理入口维护主体、资源、动作、规则，并清晰投影到 Cloudreve 与 Search |
| R6 | Cloudreve ES / Tika / 全文链路 | 文件变动、抽取、sidecar、ES upsert 保持一致，公共文件 owner 和 `tree_path` 边界正确 |
| R7 | 单节点与主从任务协调 | 压缩、解压、文件抽取、ES 同步、离线下载等任务在单节点和主从模式下职责清楚、队列可观测 |
| R8 | 管理端页面完整性 | 统一认证、网盘授权、统一检索、统一授权页面能覆盖配置、预览、运行时排查入口 |

## 5. 总体结论

三个系统当前没有出现“架构方向跑偏”。当前形态仍然符合旧设计的主方向：

1. Authverse 是统一认证中心和授权配置中心。
2. Cloudreve 是 OIDC Client 与资源服务端。
3. Search 是 OIDC Client 与检索执行端。
4. Cloudreve 公共授权与 Search 授权没有强行合成一套运行时，而是走“统一主体模型 + 统一管理入口 + 分目标投影”。
5. Cloudreve 来源的 Search 结果已经按 `baseAllow AND (ownerBoundary OR publicVisibilityBoundary)` 收敛，主方向不是扩大权限。

但当前不能认定为“完全满足旧需求”。主要偏差集中在四类：

1. OIDC 安全与契约边界仍不够硬，包括 scope、refresh token/access token 边界、redirect_uri、Search backchannel logout。
2. 统一授权 DSL 页面能力大于运行时执行能力，`visibilityRule`、`actionRules.rule`、`appendSearchRule` 三者职责仍需明确。
3. Cloudreve 与 Search 的主体语义仍有差异，尤其是 group、role ID/code、操作符 `starts_with/prefix`。
4. 真实环境回归尚未完成，尤其是浏览器单点会话、公共文件授权、ES 同步、单节点/主从任务协调。

## 7. 分系统代码核对结论

### 7.1 Cloudreve

按代码核查已满足：

1. OIDC remote binding 已落地。`oidc_config_mode=remote` 时会通过 well-known 推导 `/app-api/authz/integration/runtime/binding-config`，并拉取 `clientId/scope/discoveryUrl/ssoUrl`。
2. OIDC token 校验、刷新、撤销、backchannel logout 的主链路已经具备。
3. 公共文件授权已按“先可见，再动作”执行，前端按钮通过 capability 映射到 `download/direct_link/archive/upload/create/rename/copy/move/delete/share/metadata` 等动作。
4. 公共文件远程授权入口已具备：`/system-api/cloudreve/authz/visibility` 与 `/system-api/cloudreve/authz/action-check`。
5. ES 文档事实字段已经包含 `file_id/owner_id/tree_path/content/latest_version/attachments/snapshot_version/synchronized_at` 等核心字段。
6. 节点 capability 已包含传统任务和内容处理任务：`create_archive`、`extract_archive`、`remote_download`、`content_processing`。

按代码核查存在的偏差与风险：

1. Cloudreve 默认 scope 仍包含 `UserInfo.Read/Admin.Read/Files.Read/Files.Write/Workflow.*` 等扩展 scope，必须与 Authverse discovery、userinfo 和 SQL 初始化保持一致，否则真实联调会反复出现缺 scope。
2. `TryVerifyOIDCAccessToken()` 命中本地缓存后仍实时 introspection。这个实现有利于撤销即时生效，但和旧文档“缓存后不再远程访问”不一致，也会把 Authverse 延迟放大到 Cloudreve 每个登录态请求。
3. 公共授权远端 base URL 仍从本地 `oidc_wellknown_url` 推导，没有直接复用 OIDC runtime binding 的生效来源。登录可用不代表公共授权一定调用同一个 Authverse 实例。
4. `checkActionRemote()` 调远端 `action-check` 后又调一次 `visibility` 做本地约束，动作校验存在重复远端计算。
5. ES 字段已能支撑运行，但“上层展示字段契约”仍未彻底标准化，Search 前端展示依赖字段仍需要收口。

判断：

Cloudreve 资源侧能力大体满足旧设计，但运行时配置来源、scope、实时 introspection 性能边界、公共授权诊断仍需优化。

### 7.2 Authverse / Authz 后端

按代码核查已满足：

1. OIDC Discovery、token、userinfo、introspection、logout、revoke callback、backchannel logout 基础能力已具备。
2. Discovery 当前已声明 Cloudreve 需要的一组扩展 scope，包括 `UserInfo.Read/Admin.Read/Files.Read/Files.Write/Workflow.*`。
3. 统一授权、网盘授权、检索授权相关服务和表结构已具备，能向 Cloudreve 和 Search 输出运行时授权结果。
4. Cloudreve 授权服务支持用户、部门、角色、岗位、权限、group 等主体表达。
5. Search 授权计划能构建用户上下文，并按源、索引、策略优先级产出 query plan。

按代码核查存在的偏差与风险：

1. `OAuth2UserController` 的 userinfo 实际只认 `user.read` 或 `user_info`，与 Cloudreve 默认扩展 scope 不是一套完整语义。
2. `OAuth2TokenServiceImpl.getAccessToken()` 在查不到 access token 时会按 refresh token 查询并转换成 access token 形态返回。这扩大了 refresh token 暴露后的影响面。
3. `OAuth2ClientServiceImpl` 使用 `startWithAny()` 校验 `redirect_uri`，存在前缀匹配边界过宽风险。
4. Search 的 backchannel logout 只解析 payload 并校验 `events/aud/sub`，没有做到 JWKS 签名验真、`iss/iat/jti` 校验和重放保护。
5. 统一授权 Cloudreve runtime 投影只消费 `subjects/actions/resource binding`，没有执行 `visibilityRule` 和 `actionRules.rule`。
6. Search runtime 投影只消费 Cloudreve 继承边界和 `searchBinding.appendSearchRule`，顶层 `visibilityRule/actionRules` 不进入 Search `finalRule`。

判断：

Authverse 主体职责满足旧设计，但安全边界和 DSL 执行契约仍是三系统当前最大的偏差来源。

### 7.3 Authverse 前端

按代码核查已满足：

1. 管理端已有 OAuth2 管理入口。
2. 已有接入注册中心入口，用于统一维护系统、地址节点与 OAuth/OIDC 客户端映射。
3. 已有网盘授权入口，用于维护 Cloudreve 公共资源、策略与模板库。
4. 已有统一检索入口，用于维护检索源、索引与检索策略。
5. 已有统一授权入口，用于维护网盘资源授权与统一检索授权融合策略。
6. 统一授权页面已有 Cloudreve 资源选择、双目标预览、Search 规则构建等能力。

按代码核查存在的偏差与风险：

1. 页面能编辑和预览的 DSL 字段，比后端运行时实际执行的字段更多。
2. 规则编辑器元数据仍暴露 `starts_with`，但 Search AST 编译器实际识别的是 `prefix`。
3. 页面展示“统一主体模型”，但 Search runtime 暂不匹配 group，角色 ID/code 在 Cloudreve 与 Search 中语义也不完全一致。

判断：

页面入口基本满足旧设计，但需要把“可配置字段”和“运行时已执行字段”明确区分，否则管理员容易误判策略真实效果。

### 7.4 Search 后端

按代码核查已满足：

1. Search 前端使用 `/search/auth/config`、`/search/auth/prepare` 等接口接入 OIDC。
2. Search 查询服务通过远程 Authz 的 `/system-api/search/authz/query-plan` 获取授权后的目标索引和过滤 DSL。
3. Query 执行前会把授权 plan 转成 Elasticsearch 查询，支持 `statsOnly`、多源、多索引聚合与授权 debug 信息。
4. SearchAuthzPlanService 已能同时装载 legacy SearchPolicy 与 UnifiedAuth Search projection。
5. CloudrevePublicVisibilityAllowAugmentor 已将 Cloudreve 来源最终边界收敛为：
   `baseAllow AND (owner_id = 当前用户 OR publicVisibility)`

按代码核查存在的偏差与风险：

1. Cloudreve 来源识别仍有字符串判断：`source.code == cloudreve`、`indexCode/indexPattern` 包含 cloudreve、`documentType == disk_file`。
2. SearchPolicySubjectMatcher 支持 user/dept/role/post/permission，但没有 group 分支。
3. role 在 Search 中支持 role code 或 role ID；Cloudreve runtime 只按 role code 匹配。
4. Search 策略只保留最高优先级命中的一层策略，低优先级 deny 不会兜底拦截高优先级 allow，需要在产品和文档中明确。
5. UnifiedAuthSearchRuntimeService 对缺失 `searchBinding.enabled` 的历史/异常数据默认启用，语义偏宽。

判断：

Search 的“不能越过 Cloudreve 公共可见边界”主方向已经满足，但主体一致性、策略优先级、来源识别和 DSL 操作符需要收口。

### 7.5 Search 前端

按代码核查已满足：

1. `search-frontend/src/session/oidc.ts` 已支持加载 OIDC config、discovery 和 prepare 授权地址。
2. `search-frontend/src/api/search.ts` 已对接 `/search/sources`、`/search/overview`、`/search/dashboard`、`/search/query`。
3. 查询 payload 已支持 `sourceCodes/indexCodes/statsOnly/pageNo/pageSize`。

按代码核查存在的偏差与风险：

1. 前端能正常发起查询不代表后端授权策略完全符合预期，最终边界取决于 Authz query plan。
2. 展示字段依赖 Search 后端从 ES document 中提取，Cloudreve ES 稳定展示字段契约未完全收口前，展示仍可能随字段变化产生偏差。

判断：

Search 前端满足基础检索入口需求，主要风险不在页面调用，而在后端授权 plan 与 Cloudreve ES 字段契约。

## 9. 对旧需求的偏差判断

### 9.1 没有偏离的部分

1. 没有把 Cloudreve 和 Search 做成两个独立认证孤岛，仍由 Authverse 统一登录。
2. 没有把公共文件授权和 Search 授权简单做成 OR 放大，Cloudreve 来源检索边界已经收敛为交集。
3. 没有把所有任务都错误并入 `content_processing`，压缩、解压、离线下载仍保留独立 capability。
4. 没有让统一授权直接绕过原 Cloudreve/Search 运行时，而是通过编译/投影逐步接入，迁移风险较低。

### 9.2 明确偏离或未达成的部分

1. 旧需求期望“三系统 token 都能直接调通”，但当前 token 类型边界和 scope 契约仍没有达到稳定标准。
2. 旧需求期望“统一授权 DSL 权限”，但当前 DSL 不是所有字段都进入 Cloudreve/Search 运行时。
3. 旧需求期望“公共文件授权策略所有模板全面覆盖”，当前模板和动作矩阵存在，但页面配置、runtime 执行、Search 投影之间还要做真实回归。
4. 旧需求期望“检索在公共文件可见性基础上再加检索策略”，主链已满足，但 group、role、operator、Cloudreve source 识别仍可能造成边界偏差。
5. 旧需求期望“文件变动同步到 ES 正确”，代码链路已具备，但 50000 文件基数、全文件操作组合和单节点/主从压力回归未完成。

## 10. 建议下一步

### 10.1 先修复安全与契约边界

1. 收口 OAuth2 token 类型边界。
2. 修正 redirect_uri 校验。
3. 补强 Search backchannel logout 签名验真。
4. 统一 OIDC scope 契约。
5. 明确 SSO Cookie 签名密钥生产配置要求，并在生产环境避免默认密钥。

### 10.2 再收口统一授权 DSL

1. 明确 `visibilityRule`、`actionRules.rule`、`searchBinding.appendSearchRule` 三者职责。
2. Cloudreve 侧要么执行 `visibilityRule/actionRules.rule`，要么在页面和预览中明确“暂不执行”。
3. Search 侧统一 `starts_with/prefix`，补 group 与 role 语义一致性。
4. 预览和运行时投影都输出“最终生效规则”。

### 10.3 最后执行真实环境回归

按已有联调测试计划执行，但建议顺序调整为：

1. 三系统 OIDC 登录、刷新、登出、revoke、backchannel。
2. Cloudreve 个人文件全操作。
3. Cloudreve 公共文件全操作与越权回归。
4. 统一检索：Cloudreve 公共可见边界 + Search 策略边界。
5. 文件变动到 ES 同步，叠加 50000 文件基数。
6. 单节点与主从节点任务协调：压缩、解压、文件抽取、ES 同步、离线下载、队列监控。

同步客户端测试项 2、3 当前按前置要求暂不纳入本轮优先回归。

## 11. 当前最终判断

截至 2026-05-21，三个系统“主架构方向满足旧设计”，但“交付成熟度尚未完全满足旧需求”。

当前真正需要优先处理的不是重新设计，而是：

1. 把 OIDC/OAuth2 安全边界做硬。
